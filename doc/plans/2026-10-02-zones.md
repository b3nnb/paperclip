# Zones V1 — one active lane per company

Date: 2026-10-02
Branch: `feat/zones-v1`
Status: shipped (schema + server invariant + UI)

## Summary

Projects carry a focus **zone**: zone **b** is THE one active lane a company
works in at a time; zone **a** is parked ideas with zero burn. V1 adds the
`projects.zone` column (`'a' | 'b'`, DB default `'a'`), enforces a
single-active-lane invariant on the server, and surfaces zones in the board
UI:

- **Data**: `packages/db` schema + migration `0295_lively_rockslide`;
  `Project.zone?: ProjectZone` (optional so legacy rows and fixtures are
  untouched — undefined parks in zone "a").
- **Constants** (`packages/shared/src/constants.ts`): `PROJECT_ZONES`,
  `ProjectZone`, `PROJECT_ZONE_LABELS`, `PROJECT_ZONE_HINTS`. All UI strings
  come from these maps — nothing is hardcoded in the UI.
- **Server** (`server/src/services/projects.ts`): promoting a project to
  zone "b" (via update or direct create) transactionally demotes every other
  zone-"b" project in the same company back to zone "a". Covered by
  `server/src/__tests__/project-zone-routes.test.ts` (5/5 green).
- **UI**: zone chip (gray brand family = parked, blue brand family = active
  lane) + popover picker on the project detail header and on every project
  card; the Projects page groups the **Zone B section first**, then Zone A,
  then projects the operator left. Optimistic save with revert-on-failure on
  the detail page; list refetch on the cards.

## One-active-lane invariant

Invariant: **at most one zone-"b" project per company, always.**

The server owns the invariant; the UI never tries to demote siblings
itself. `demoteOtherZoneBProjects(dbOrTx, companyId, excludeProjectId)` runs
inside the SAME transaction as the promote (update path) or insert (create
path), so the two writes commit or roll back together — a reader can never
observe two zone-"b" rows for one company, even mid-flight. Self-demotions
to zone "a" and zone-less updates keep the cheap single-statement path.

## Rename plan

The feature is provisionally named "zones". Every user-visible string lives
in `PROJECT_ZONE_LABELS` / `PROJECT_ZONE_HINTS` in
`packages/shared/src/constants.ts` (single file), and the Projects page
section titles are composed from those constants — so renaming to "lanes",
"focus", or anything else is a one-file edit in `@paperclipai/shared` plus
re-running the two page test files, which assert against the same
constants. The bare zone keys (`'a'`/`'b'`) are data values and are NOT
renamed.

## V2 backlog

- **Zone-based wake guards**: heartbeat wake/agent scheduling should treat
  zone "a" (parked) projects as zero-burn — skip wake-ups and daemon work
  until the operator promotes the project back to the active lane.
- **Partial unique index hardening**: back the invariant with a partial
  unique index (`CREATE UNIQUE INDEX ... ON projects (company_id) WHERE
  zone = 'b'`) so even a bug that bypasses `projectService` cannot produce
  two active lanes; the transactional demote remains the primary mechanism,
  the index is the seatbelt.
- **Zone in activity-log details**: record `zone` transitions (promote /
  demote, including the sibling demotions the server performs) in the
  activity log so operators can see who moved the active lane and what got
  parked as a result.
- **Sidebar integration**: surface the zone chip / active-lane marker in
  the sidebar project list, not just the Projects page and detail header,
  so the active lane is visible everywhere projects appear.
